## 三、任务目标

生成一份技术说明文档，帮助读者理解：

1. 论文试图解决什么问题，任务的输入与输出是什么。
2. 论文提出了哪些核心方法组件，以及这些组件如何协作。
3. 代码仓库中的哪些模块、类、函数和数据结构实现了这些方法。
4. 论文描述与实际代码实现之间有哪些一致之处和差异。
5. 代码中有哪些论文未说明或未详细说明的工程实现细节。
6. 在当前环境下，哪些运行或测试可以实际完成，验证结果有哪些局限。

重点是建立**论文方法与代码实现之间可追溯的对应关系**，而不是泛泛介绍论文、仓库目录或实验结果。

## 四、分析原则

### 证据与可信度

对重要结论进行来源标注：

- 论文证据：章节、公式、图、表、页码或附录位置；
- 代码证据：文件路径、类名、函数名；可行时注明行号；
- 实验或运行证据：实际执行的命令、环境与观察到的结果。

明确区分以下四类内容：

1. **论文明确说明**：可在论文中找到直接依据；
2. **代码直接确认**：可从实现中直接观察到；
3. **根据代码推断**：对代码行为的解释，但论文或代码没有直接说明；
4. **尚未确认**：当前资料不足以得出结论。

推断和未确认事项必须明确标注，不能写成已证实的事实。不要编造公式、参数、张量形状、代码位置、运行结果或实验结论。

### 论文与代码术语

- 优先使用论文中的方法名称，同时注明代码中的实际命名。
- 如果论文名称和代码名称不同，解释它们的对应依据。
- 不要仅因名称相似，就认定论文方法与代码模块一一对应。
- 如果某个论文组件在仓库中找不到实现，说明已检查的范围和未确认原因。

### Issue、讨论和外部资料

- Issue 或讨论内容可以作为问题背景和排查线索，不能替代论文与代码证据。
- 不要仅凭 Issue 标题推断问题的原因、解决方案或项目行为。
- 对使用的外部资料注明来源；如果资料互相矛盾，指出差异，不要自行掩盖。

## 五、建议工作流程

### 1. 检查项目与资料

- 检查仓库结构、README、配置文件、环境说明、运行脚本、测试和关键依赖。
- 阅读论文中与方法有关的正文、公式、图表及附录。
- 搜索与核心方法相关的模型定义、数据处理、训练、推理、评估和可视化代码。
- 优先沿着一条有证据支持的实际数据流进行分析，避免无目的地罗列文件。

### 2. 梳理论文方法

说明：

- 任务定义和问题背景；
- 方法的输入、输出和假设；
- 核心组件及其职责；
- 组件之间的数据流和信息传递；
- 论文中的关键公式、损失函数、训练目标或推理步骤；
- 论文报告的实验设置中与理解方法直接相关的内容。

不要把论文背景或实验结果扩展成方法本身。仅在有论文证据时陈述论文结论。

### 3. 追踪代码实现

尽量从项目入口或实际运行入口出发，追踪核心数据流：

- 输入如何读取、预处理和组织；
- 数据经过哪些模块；
- 各模块接收和返回什么；
- 模型、优化器、后处理或评估逻辑在哪里实现；
- 输出如何保存、转换或传递给下游。

对张量、数组或结构化数据，只有在代码确认后才填写形状及维度含义。不确定时写“未确认”，并说明需要检查什么才能确认。

### 4. 比较论文与实现

检查并说明：

- 代码是否实现了论文中描述的核心组件；
- 实现是否增加、简化、替换或省略了某些步骤；
- 配置默认值、预处理、后处理、数值处理、缓存、批处理等工程细节；
- 论文没有详述但代码实际采用的设计；
- 代码中看似对应某方法、但目前缺少充分证据的部分。

不要把所有代码差异都称为论文方法差异。区分方法层面的差异与工程实现细节。

### 5. 运行与测试（按项目适用）

先检查项目已有的环境配置和测试说明，再选择适当方式验证。

- 使用项目已有的环境管理方式，例如 Conda、venv、Docker、uv 或仓库指定工具；不要假定所有项目都应使用 Conda。
- 如果创建环境，尽量使用独立环境，不覆盖已有环境。
- 如果需要数据集、权重、服务凭据、GPU 或其他资源，先检查其是否可用。
- 不要在未经许可或不必要的情况下下载大型文件、上传数据或调用付费服务。
- 缺少真实数据时，可以在安全且合理的前提下使用合成数据、临时输入或 mock，验证有限的代码路径。
- 如果无法安全构造有效输入，不要强行伪造测试；记录未能运行的原因即可。
- 不要为了通过测试随意修改核心逻辑。若确需临时改动，记录并在结束前恢复，或明确指出未恢复的改动。
- 仅报告实际执行过的命令和观察到的结果。
- 合成数据、mock 或局部测试只能证明相应代码路径被触发或可运行，不能证明论文结果已复现、模型输出正确或性能达到论文水平。

### 6. 避免无关改动

除生成指定文档及确有必要的环境或测试文件外，不要修改项目核心代码或无关文件。

如果目标文档已存在，先检查其内容，再决定更新、补充还是另存为新文件。不要覆盖重要文件。

## 七、文档结构

请使用以下结构；不适用的部分可以说明原因后省略。

1. **文档目的与分析范围**
   - 仓库版本或提交信息（如果可获得）
   - 论文版本与资料来源
   - 读者预备知识
   - 分析限制

2. **研究问题与任务定义**
   - 解决的问题
   - 输入、输出和关键假设
   - 必要背景概念

3. **论文方法总览**
   - 用简明流程图、Mermaid 图或有序步骤展示方法的数据流
   - 解释主要组件之间的关系

4. **核心方法逐项说明**
   对每个主要组件说明：
   - 论文中的名称、作用及证据位置；
   - 输入与输出；
   - 关键处理步骤；
   - 对理解有帮助的公式或伪代码；
   - 对应代码位置；
   - 论文描述与代码实现的差异或未确认事项。

5. **论文方法—代码实现对照表**
   建议列出：
   - 论文术语；
   - 论文中的作用；
   - 代码符号及路径；
   - 输入与输出；
   - 对应依据；
   - 实现备注与不确定性。

6. **端到端数据流**
   - 从项目入口到核心计算，再到最终输出
   - 必要时给出关键函数的调用顺序

7. **论文未覆盖或未详细说明的实现细节**
   - 区分代码直接确认的事实与推断
   - 说明这些细节可能影响的运行、复现或结果解释

8. **运行与验证**
   - 使用的环境及其来源
   - 实际执行的命令与结果
   - 测试覆盖范围
   - 失败原因、资源限制及验证局限

9. **新读者的阅读路径**
   - 建议依次阅读的文件、类和函数
   - 说明每项的阅读目的

10. **术语表与参考资料**
   - 解释重要术语和缩写
   - 列出论文、代码文件、项目文档及其他引用来源
